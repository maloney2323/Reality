# Reality · Genuine Capability Engine v1

## Purpose
One original customer job can discover a missing reusable capability and
recover without changing goals, creating a replacement job, or manually
installing model-generated files. This is an evidence-bound *engine*, not a
dashboard, a list of GitHub issues, or a synthetic success counter.

## Source of truth
The caller must independently obtain:
1. An authenticated, active owner goal and original work scope.
2. An **observed failure** from a read-only, separately trusted provider.
3. A second independent provider readback of the exact same failure.
4. A **reproduced failure** in a pinned, independently verified frozen suite.
5. A provider-verifiable absence of the required capability in its registry.

No model text, issue title, web page, or confidence score can substitute for
any of these. Transient network failures, authorization gaps, unverified claims,
uncertain external side effects, and preexisting capabilities are not eligible
for generation.

## Engine behavior
`createGenuineCapabilityEngine` composes the real execution failure with
Reality's existing `continueOriginalJobFromVerifiedCapabilityGap` and
`continueGovernedSelfImprovement` constitutional driver. The driver must
receive trusted adapters for generation, independent sandbox, durable checkpoint,
and independent receipt verification.

The existing driver owns the stages:

```
Running original work
    -> independent missing-instrument observation
    -> provider reobservation + frozen reproduction + registry absence
    -> original-goal immutable GAP_CONFIRMED checkpoint
    -> model candidate and its own test proposal
    -> network-isolated independent frozen/candidate tests
    -> bounded correction with independent failure receipts
    -> AWAITING_OWNER_APPROVAL (STOP)
    -> one signed-in exact artifact promotion authorization
    -> provider-backed preview installation + readback
    -> ACTIVE capability registry readback
    -> resume SAME original work ID
    -> independent original outcome + durable final settlement
    -> separate customer acceptance
```

The original work ID, goal transition, artifact hash, owner, and environment
remain bound across stages. The model cannot write its own approval, registry
admission, or settlement.

## Internal executor integration
`createGenuineCapabilityExecutionHandoff` plugs directly into
`executeAuthorizedWork({onVerifiedCapabilityGap})`. It independently
compares the executor's failure to the provider readback, then requires a
durable, independent receipt for the handoff. A handoff still leaves the
original execution **UNRESOLVED**, not falsely completed.

## Genuine multi-business evidence
Provider receipts can be either tightly scoped existing Reality GitHub/Vercel
references or typed `reality:provider-verified:<adapter>:<id>` references.
New business connectors must implement an independent trusted provider
adapter. Typed references alone confer no credibility.

## Operational pass condition
**PASS** only when one new genuine customer job produces distinct verified
receipts for failure, gap, source generation, independent test, exact
one-time owner approval, post-approval installation, capability activation,
same-job resumption, settlement and customer acceptance—with **no manual
source edit/merge** and no production changes.

A green unit test, isolated sandbox test, or previously installed candidate
is never a substitute for the live customer proof.
